# 修订与审查检查表

按任务规模使用，不要求每次普通润色执行全部项目。

## 1. 快速检查：直接编写与文字润色

- 是否保持用户原有研究意图、技术含义、数值和证据强度？
- 术语、缩写和符号是否与 `thesis-terminology.md` 一致？预测值是否使用 `\hat{}`，宽深通道的 `W`、`D` 是否为下标？
- 是否删除了空泛背景、重复结论、宣传性形容词和机械连接词，而未删除必要技术细节？
- 每段是否承担清晰功能，句间逻辑是否由真实的因果、比较、转折或递进关系支撑？
- 缺少的引文、数值或方法细节是否保留了具体占位，而非被模糊表述掩盖？

## 2. 修改前 Git 备份

本节只适用于已纳入 Git 的论文文件，并在大范围修改、章节重排或批量交叉引用调整之前执行。

- 先检查仓库状态以及待修改文件在工作区和暂存区中的状态，确认目标文件是否已跟踪、是否存在未提交内容，并识别其他文件已有的修改、暂存和删除状态。
- 若待修改文件存在未提交内容，在开始修改该文件前，将其当前完整状态提交到本地 Git 作为备份。备份提交只能包含本次即将修改的目标文件，不得顺带提交、暂存、取消暂存、还原或删除其他路径的改动。
- 创建备份时使用仅限定目标路径的提交方式，并在提交后核对提交所含文件。不得使用会覆盖或重排无关工作区状态的全局暂存、重置、清理或临时存储操作。
- 若目标文件工作区和暂存区均干净，且当前版本已经存在于 Git 历史中，不创建空提交。
- 备份提交只保存在本地，不推送远程，也不借此修改分支历史。
- 若目标文件未被 Git 跟踪，或因仓库状态、权限、身份配置、冲突等原因无法完成必要备份，应先报告并解决备份问题，再进行批量修改。

## 3. 方法与公式专项检查

- 是否核对了目标实验对应的代码提交、执行入口、配置和保存产物？无法访问代码时是否明确说明？
- 是否检查了实际 `forward` 或等效执行路径，而非只根据文件名、类名、README 或旧论文描述推断？
- 论文是否只把“DynaGS 模型”作为正式模型名称？源码标识 `TFPP` 是否仅用于必要的代码对应说明，而未被写成独立模型、子模型或创新点？
- 模型输入、输出、索引范围、张量维度、广播和聚合关系是否逐项定义并与代码一致？
- 同一数学对象是否始终使用相同符号？同一符号是否被用于不同对象？新增符号是否与总表冲突？
- Markdown 行内公式是否使用 `$...$`、独立公式是否使用 `$$...$$`，且公式仍为可编辑的标准 LaTeX，而非图片、UnicodeMath 专有写法或依赖未说明宏包的表达？
- 公式编号是否留给最终排版流程？用户要求“Word 可复制公式”时，是否额外提供了不含数学分隔符和代码围栏的纯 LaTeX 源码？
- 涉及 Pandoc 或 Word 转换时，是否分别核查数学含义、视觉显示和源码字符串一致性，且未把“数学含义一致”误写成“源码完全相同”？复杂公式未经实际转换时是否避免声称已经兼容？
- DynaGS 模型的完整模式、源码消融标识 `wide`、`deep`、`add` 及融合公式是否与当前实现一致？
- 损失函数、优化器、学习率、早停、筛选数量和其他超参数是否来自具体实验，而非配置默认值或可选能力？
- 模型设计动机是否被误写为实验结论或生物学机制？
- RoPE 与 ELU+1 的执行顺序是否与实际代码一致（已核查版本为先对查询、键施加 RoPE，再作 ELU+1 特征映射），是否避免照搬 RoFormer 原论文组合公式？
- 时间查询是否按预设观测时间点初始化并作为可学习参数；是否统一表述“预设观测时间点上的联合预测”而未声称对任意未见时间点预测？
- 门控网络初始化（权重标准差 `10^{-5}`、偏置 `-5`）是否与定稿代码版本核对一致？时间基矩阵是否为初始化阶段计算的非可学习缓冲，且 `\tau_{\max}-\tau_{\min}\le 10^{-6}` 的特殊处理如实描述？
- 宽通道输入是否为类别码还原剂量后缩放至 `[0,1]` 并经众数填补；损失函数是否基于标准化尺度符号 `\tilde{y}_{i,p,t}`、`\hat{\tilde{y}}_{i,p,t}`，MSE 分母为 `BPT`？
- 符号是否遵循术语与符号表：`K`/`K_s`/`K_{\mathrm{CV}}` 分工、`\Phi` 时间基矩阵、`\Psi` 正态分布函数、形状使用普通 `R`？

## 4. 实验与结果专项检查

- 样本、表型、时间点、SNP 数、纳入规则和数据尺度是否明确且可追溯？
- 训练、验证和测试是否按个体互斥？预处理、缺失填补、筛选、归一化和模型选择是否只使用允许的数据？
- 基线是否使用可比的数据划分、输入、预处理、调参预算、测试次数和指标实现？不等价条件是否披露？
- 最终测试是否与验证调参分离？交叉验证的折、随机种子或独立数据集是否被正确识别为重复单位？
- PCC、R²、MSE、RMSE、MAE 的公式、方向、聚合方式和尺度是否准确？当前 R² 是否明确为时间校正全局口径？
- 均值、标准差、标准误、置信区间和显著性检验是否正确命名？报告的精度是否超过结果稳定性？
- 每项结论是否有对应数值和比较条件？负面、不一致或高变异结果是否被如实说明？
- 消融结果是否仅支持当前条件下的组件贡献，而未被解释为唯一机制或生物学证明？

## 5. 全文一致性与证据链检查

- 正式目录是否来自用户或学校材料？是否把推测的章节结构误当成定稿目录？
- 摘要、研究问题、研究目标、创新点、方法设计、实验问题、结果和最终结论是否一一对应？
- 绪论是否提出问题，理论章节是否提供必要基础，方法章节是否说明本文实现，实验章节是否提供证据，总结是否在证据范围内作答？
- 不同章节的模型名称、术语、英文缩写、公式、数据集、样本量、时间点、超参数和指标值是否一致？
- 同一模型结构是否在不同章节出现互相冲突的描述，例如“加权平均”与“残差式门控融合”混用？
- 正文、摘要、目录、图表标题、图例、公式说明和创新点中是否残留“TFPP 模型”“TFPP 网络”“DynaGS 框架”等非统一称呼？
- 文献结论、代码实现、实验发现和作者推断是否可以清楚区分？引用是否真正支持相邻论断？
- 创新点是否在方法中落实并由实验验证？是否存在只在摘要或总结中出现的强结论？
- 局限是否具体说明对解释或泛化的影响，展望是否从局限或未解决问题自然导出？
- 各章节是否承担正式目录规定的功能？同一公式是否只在最合适的位置完整介绍，其余章节通过引用承接？
- 术语是否统一：无“通路”“确定性”“DynaGS 框架”等表达；DC-SIS 首次出现是否使用完整中英文及缩写？

## 6. 交叉引用审查

本节审查正文中的章节、小节、图表和公式等内部交叉引用，不替代参考文献真实性核查。

- 逐处检查引用编号是否存在、目标标题是否正确，并判断引用是否准确概括目标位置实际讨论的内容。不得因编号正确就默认引用成立。
- 判断引用是否有必要。若目标内容紧接在下一小节、读者无需额外定位即可看到，通常删除“将在下一节介绍”等预告；反复出现的“具体内容将在某章介绍”等空泛提示也应删除。
- 对跨越较远篇幅、能够帮助读者定位方法、实验设置、结果或论证依据的引用予以保留，并尽量指向具体小节、图表或公式，避免只笼统指向整章。
- 引用句被删除、缩短或改写后，立即检查所在句和段落的主谓宾、逻辑关系、句末标点及前后衔接，清除残句、悬空逗号、重复连接词和失去指代对象的表达。
- 完成局部修改后，通查正文、目录及相关章节的标题和编号，确认显示编号、引用文本与实际目标一致；目录或标题发生变化时，应重新检查所有受影响引用。

## 7. 冲突处理与更新建议

发现冲突时按以下顺序处理：

1. 记录冲突位置和两种表述，不静默选边。
2. 核对真实代码和实验产物；再核对用户确认的论文材料与可靠文献。
3. 给出推荐统一表述、选择依据和受影响章节。
4. 建议更新 `thesis-terminology.md` 中相应术语或符号，并列出需要同步的公式、图表和摘要位置。

无法持久化修改项目文件或其他对话内容时，只提供明确的同步清单，不声称已经自动更新。

## 8. 最终输出检查

- 用户要求直接写作或修改时，是否优先提供完整、连贯、可直接使用的正文？
- 论文正文是否以 Markdown 输出，并仅使用与论文结构相符的标题、段落、公式、引用、必要列表和表格？
- 正文、摘要和图表说明中是否清除了加粗、高亮、装饰性提示框、表情符号及其他非论文式视觉强调？是否避免用行内代码格式强调普通术语？
- 用户要求分析或审查时，是否清楚列出问题、依据或原因及可执行修改？
- 是否虚构了引文、方法、参数、数据、统计检验、数值结果或学校格式？
- 是否只保留真正影响使用的待确认项，避免反复输出泛化风险说明？
- 中文表达是否专业自然、信息充足，且没有以“降重”或“去 AI 化”为名牺牲准确性和可复现性？
